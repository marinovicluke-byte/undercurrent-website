## Vercel / Deploy

- **Vercel build fails with "No Output Directory named dist"** — Vercel project is still configured for Vite. Fix: Vercel dashboard → Settings → Framework Preset → Next.js. Do NOT change until ready to deploy redesign. (Resolved 2026-04-20, see Cutover section.)
- **Workspace root lockfile warning — NOT cosmetic under Next.js 16 Turbopack.** Old note said "cosmetic only", wrong. Under Next 16 Turbopack, the auto-detected root becomes the module resolution root. When the parent `/Website/` had a stray `package.json` + `package-lock.json`, Turbopack picked the parent as workspace root and could not resolve `tailwindcss` (installed in `undercurrent/node_modules` only). Every CSS file errored on every request, flooding stderr, OOMing the Node process, crashing the laptop twice on 2026-04-19. Fix: (1) pin `turbopack.root` to `__dirname` in `next.config.mjs` (done), (2) renamed parent `package.json` and `package-lock.json` to `.bak` so only the real `undercurrent/package-lock.json` remains.
- **2026-04-28 `vercel deploy --target=preview --yes` from CLI fails with "No Next.js version detected".** Run from `undercurrent/` (correct dir, valid `package.json` with `next` dep), still errors. Vercel project's Root Directory setting causes the CLI deploy path to mismatch. Workaround: push an empty commit (`git commit --allow-empty -m '...' && git push`) to let Vercel's GitHub integration auto-deploy. Don't try to fix by re-linking or running `vercel deploy` from the parent dir — same outcome.
- **2026-04-28 `vercel env add NAME preview --yes` refuses to resolve to "all preview branches" non-interactively.** Even though the help text says omitting the branch argument means "all preview branches", `--yes` aborts with `git_branch_required`. Must either scope to a specific branch (`vercel env add NAME preview <branch> --value <v> --yes`) or set via the dashboard. Production env adds work fine without branch scoping.

## CSS / Inline Styles

- **`clamp()` inside a CSS custom property fails silently in React inline style shorthands.** Using `--page-pad: clamp(42px, 6.8vw, 180px)` then `padding: '120px var(--page-pad)'` rendered at 0px left padding — no error, just silent fallback. Fix: put a simple px value in the variable (`--page-pad: 88px`) and handle responsiveness via `@media` override on `:root`. Potential lesson for other projects.

## Frontmatter conventions
- **2026-05-20 Article "last updated" frontmatter field is `dateModified`, NOT `updated`.** The live App Router route `app/blog/[slug]/page.js` reads `fm.dateModified` for both the OpenGraph `modifiedTime` (line 44) and the Article JSON-LD `dateModified` (line 155); it falls back to `fm.date` if absent. The legacy SPA component `src/views/Article.jsx` used `article.updated` — that field name is dead on the production route. Adding `updated:` to article frontmatter is a silent no-op: the schema keeps showing the original publish date. Fix is to use `dateModified: "YYYY-MM-DD"`. Potential lesson: when bumping an article's freshness signal, set `dateModified` in frontmatter and verify the live JSON-LD flipped via `curl … | grep dateModified` — don't trust the field name from the older component.

## Content quality workflow
- **2026-05-25 Audit-grade-retrofit pattern for glossary batches.** Workflow that surfaced the 1-of-1 angle without rewriting the whole batch: (1) write the batch end-to-end on a worktree, (2) ship to main, (3) honestly grade each entry on a 4-criteria rubric (citeable line, original example, contrarian stake vs consensus, declared UC opinion), (4) sort into 1-of-1 / differentiated / encyclopedia-shaped buckets, (5) retrofit only the encyclopedia-shaped ones with a first-principles contrarian take, (6) /humanizer pass, (7) re-grade. Batch-5 result: avg jumped 7.7 → 8.5 with surgical edits to 3 of 10 entries. The grading rubric works because it forces the question "what would a competitor's glossary refuse to write?" — that's where the 1-of-1 lives. Reusable for any client content where the first pass lands competent-but-forgettable. Potential lesson: don't audit during the write (slows the batch), audit AFTER shipping when you can read with fresh eyes. Cross-project candidate.

- **2026-05-04 Duplicate H1 in source HTML across all blog articles + case studies.** Page templates render frontmatter `title` as the visible page `<h1>`. Markdown bodies start with a `# Heading` line, which `remark-html` compiles to a SECOND `<h1>` inside `bodyHtml`. CSS `.article-prose h1 { display: none }` and `.cs-prose h1 { display: none }` were hiding the duplicate visually — but `display:none` does NOT remove the element from source HTML, so crawlers and AI engines saw two competing topic signals per page. Verified bug across 24 articles + 2 case studies via `curl … | grep -c '<h1'`. Fix: added 5-line `stripLeadingH1` remark plugin to `lib/articles.js` and `lib/caseStudies.js` that drops the leading H1 node from the AST before HTML rendering, plus a build-time guard that throws if any compiled article HTML still contains an `<h1>`. Removed the now-redundant `display:none` CSS rules. Verified post-deploy via curl across all live URLs: every article + case study + cluster + service page ships with exactly one `<h1>`. Potential lesson: when a CSS rule exists to hide a structural element, ask why it's being rendered in the first place — `display:none` cannot fix SEO/AIO concerns, only AST/source-level fixes do. Cross-project candidate.
